# Расширение 1С:Управление торговлей 10.3 для ЭДО через «Платформа ЭДО»

Отправка исходящих УПД (СЧФДОП) формата **5.03** из УТ 10.3 оператору ЭДО
[«Платформа ЭДО»](https://edo.platformaofd.ru): сборка титула продавца, ФЛК оператора,
**подпись КЭП на стороне сервера 1С**, отправка и запись результата обратно в базу.

🔑 **Ключевое отличие от коробочного сценария — подпись выполняется на сервере.** Контейнер КЭП
лежит в реестре под учёткой службы кластера, сертификат — в её личном
хранилище.

## Требования

- **1С:Предприятие 8.3.18+** для работы (режим совместимости расширения — `Version8_3_18`)
- **1С:Предприятие 8.3.20+** для сборки — исходники выгружены в формате **2.17**
- **УТ 10.3** (обкатано на 10.3.88.3);

⚠️ Версию формата XML-выгрузки выбрать нельзя: её штампует та платформа, которая выгружает,
и режим совместимости на это не влияет. Старшая платформа читает более ранние форматы, младшая
новые — нет. Поэтому дерево держим в 2.17 (8.3.20–8.3.24): так исходники открываются и на 8.3.2x,
и на 8.5. ⟹ **выгружать `src` обратно только платформой 8.3.20–8.3.24**, иначе формат уедет вверх
и соразработчики на 8.3.x потеряют доступ к исходникам.

## Готовая сборка

Собранный `.cfe` каждой версии — на вкладке
[Releases](https://github.com/rsyuzyov/platformaedo-ut103/releases), рядом лежит файл с SHA-256.
Номер релиза совпадает с `<Version>` расширения: `v1.0.3.3` = `1.0.3.3` в свойствах расширения
в базе, так что установленную сборку всегда видно.

## Сборка `.cfe` из исходников

```powershell
powershell -ExecutionPolicy Bypass -File build\build.ps1 `
    -Bin  'C:\Program Files\1cv8\8.3.24.1439\bin\ibcmd.exe' `
    -Src  '.\src' `
    -Out  '.\PlatformaEDO.cfe'
```

## Выпуск релиза

Собрать `.cfe` в облачном раннере нельзя — нужна платформа 1С, поэтому релиз выпускается
с машины, где она установлена:

```powershell
powershell -ExecutionPolicy Bypass -File build\release.ps1 -DryRun   # прогон без публикации
powershell -ExecutionPolicy Bypass -File build\release.ps1           # тег + релиз на GitHub
```

Скрипт берёт номер из `src/Configuration.xml`, находит `ibcmd` сам (предпочитая 8.3.20–8.3.24),
собирает `.cfe`, считает SHA-256, ставит тег `v<версия>` и публикует релиз через
[`gh`](https://cli.github.com/) с заметками из истории коммитов. До сборки он отказывается
работать, если рабочая копия не чиста, ветка не `main`, локальная `main` разошлась с `origin`
или тег такой версии уже есть — во всех этих случаях выпущенный файл не соответствовал бы тегу.

Ключи: `-Bin` (путь к `ibcmd.exe`), `-Out` (каталог артефактов, по умолчанию `dist\`),
`-NotesFile` (свои заметки вместо сгенерированных), `-Draft`, `-SkipChecks`.

## Проверки исходников

`build/checks.py` проверяет то, что читается без платформы: версия расширения, версия формата
выгрузки, разбор XML, отсутствие в публичном дереве следов конкретной базы и — главное — что
версия поднята, если `src` менялся после последнего релиза. Тот же скрипт гоняется в GitHub
Actions на каждый push и pull request.

```powershell
python build\checks.py
```

## Настройка

### 1. Свойства объектов

Расширение хранит своё состояние в типовом механизме свойств
(ПВХ `СвойстваОбъектов` + регистр `ЗначенияСвойствОбъектов`) — своих регистров оно не заводит,
поэтому установка не требует реструктуризации базы и монопольного режима.

Завести до первой отправки:

| свойство | назначение | тип |
|---|---|---|
| `ОФД_ЭДО_СтатусДокумента` | статус отправки документа | Число (3,0) |
| `ОФД_ЭДО_ИдентификаторДокумента` | идентификатор документа у оператора | Строка (50) |
| `ОФД_ЭДО_ИдентификаторУчастникаЭДО` | идентификатор абонента у контрагента | Строка (50) |
| `ОФД_ЭДО_СтатусСвязи` | состояние приглашения/связи с контрагентом | Строка (50) |
| `ОФД_ЭДО_Фамилия`, `ОФД_ЭДО_Имя`, `ОФД_ЭДО_Отчество` | ФИО подписанта организации-продавца | Строка |
| `ОФД_ОРГ_Фамилия`, `ОФД_ОРГ_Имя`, `ОФД_ОРГ_Отчество` | ФИО подписанта в узле `Подписант` | Строка |
| `ОФД_ОРГ_Должность` | должность подписанта; для ЮЛ по умолчанию «Руководитель», для ИП «Индивидуальный предприниматель» | Строка |
| `ОФД_КА_Фамилия`, `ОФД_КА_Имя`, `ОФД_КА_Отчество` | ФИО подписанта контрагента | Строка |

⚠️ Ресурс `Значение` регистра — **Строка(50)**. Списки и длинные значения туда не влезают,
поэтому кэши и настройки расширение держит в `ХранилищеОбщихНастроек` (см. ниже).

### 2. Параметры в `ХранилищеОбщихНастроек`

Объект `ОФД_ЭДО_НастройкиОбработки`:

| ключ | что хранит |
|---|---|
| `ОтпечатокПодписанта` | отпечаток сертификата КЭП (Base64) — **обязателен**, в коде его нет |
| `Хост` | адрес API оператора |
| `КлиентскиеНастройки` | XML-настройки движка вендора |
| `РеестрАдресов`, `ФактическиеМаршруты` | кэш адресов контрагентов и фактических маршрутов доставки |
| `ЗамокОтправки` | защита от одновременной отправки одного документа двумя сеансами |

Отпечаток задаётся так:

```bsl
ХранилищеОбщихНастроек.Сохранить("ОФД_ЭДО_НастройкиОбработки", "ОтпечатокПодписанта", "<base64>");
```

## Ограничения и известные грабли

- маппинг в макете `НастройкаРеализация` **привязан к конкретной конфигурации базы**: он
  обращается к реквизитам документа реализации, именам видов контактной информации и составу
  перечисления статусов заказа. На другой базе эти места придётся сверить — они снабжены
  комментариями прямо в макете;
- маппинг лежит **в макете расширения**, а не в настройке базы ⟹ любая его правка требует
  пересборки `.cfe`;
- ⚠️ макет — это XML, а BSL лежит внутри его узлов. Сырые `<` и `>` в комментариях BSL ломают
  разбор макета, и сборка документов падает уже в бою. Экранировать (`&gt;`) или не писать;
