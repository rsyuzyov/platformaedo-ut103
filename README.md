# ПлатформаЭДО — расширение 1С:Управление торговлей 10.3 для ЭДО через «Платформа ЭДО»

Отправка исходящих УПД (СЧФДОП) формата **5.03** из УТ 10.3 оператору ЭДО
[«Платформа ЭДО»](https://edo.platformaofd.ru): сборка титула продавца, ФЛК оператора,
**подпись КЭП на стороне сервера 1С**, отправка и запись результата обратно в базу.

Расширение работает в бою с 13.08.2026 в двух организациях; за это время им отправлено
несколько тысяч документов, включая накладные с кодами маркировки «Честного ЗНАКа».

## Что внутри

| объект | чей | зачем |
|---|---|---|
| `DataProcessors/ПЭДО_ПлатформаЭДО` | вендор | движок оператора: XML по схеме, ФЛК, транспорт, формы работы с ЭДО |
| `DataProcessors/ПЭДО_Помощник` | наш | маппинг УТ 10.3 → УПД 5.03 (макет `НастройкаРеализация`) и форма отбора документов к отправке |
| `CommonModules/ПЭДО_Сервер` | наш | серверный сценарий: собрать → ФЛК → подписать → присоединить подпись → записать статус |
| `CommonModules/ПЭДО_Клиент` | наш | клиентский фасад и фолбэк, если серверного ключа нет |
| `CommonCommands/ПЭДО_ОтправитьПоЭДО` | наш | команда «Отправить по ЭДО» в форме документа |
| `Catalogs/Контрагенты`, `Catalogs/Организации` | заимствованы | реквизиты ИНН/КПП нужны формам вендора |

Свойства расширения: имя `ПлатформаЭДО`, префикс `ПЭДО_`, назначение `Customization`,
режим совместимости **8.3.18**.

🔑 **Ключевое отличие от коробочного сценария — подпись выполняется на сервере.** Контейнер КЭП
лежит в реестре под учёткой службы кластера (`<ДОМЕН>\USR1CV8`), сертификат — в её личном
хранилище. Поэтому отправка возможна из фонового задания, регламента или обработки проведения,
без участия клиента и без round-trip в браузер.

## Требования

- **1С:Предприятие 8.3.18+** (расширение собрано платформой 8.5.1; см. «Сборка» — версия формата
  выгрузки важнее версии кластера);
- **УТ 10.3** (обкатано на 10.3.88.3);
- **КриптоПро CSP** на сервере 1С, контейнер и сертификат под учёткой службы кластера;
- договор с оператором «Платформа ЭДО» и доступ к его API;
- исходящий HTTPS на `edo.platformaofd.ru`.

## Сборка `.cfe` из исходников

Нужна только платформа — ни рабочей базы, ни конфигуратора. Пустой файловой ИБ достаточно,
несмотря на заимствованные объекты:

```powershell
powershell -ExecutionPolicy Bypass -File build\build.ps1 `
    -Bin  'C:\Program Files\1cv8\8.5.1.1343\bin\ibcmd.exe' `
    -Src  '.\src' `
    -Out  '.\PlatformaEDO.cfe'
```

Что делает скрипт: `infobase create` → `config extension create` → `config import` → `config save`.

- ⚠️ **`ibcmd config import` не понимает `--force`** (в отличие от `load`, `export` и `check`).
  С этим флагом шаг падает `exit=2`, а следующий `config save` спокойно сохраняет **пустое**
  расширение и возвращает `exit=0`. Ловится только сверкой размера: несколько килобайт вместо
  ожидаемых сотен. Скрипт проверяет и код возврата каждого шага, и размер результата.
- ⚠️ Собирать можно платформой новее кластера-приёмника: ограничение лежит на версии формата
  выгрузки исходников, а не на контейнере `.cfe`.

## Установка

```
1cv8 DESIGNER /S<сервер>\<ИБ> /N<пользователь> /P<пароль> ^
      /LoadCfg PlatformaEDO.cfe -Extension ПлатформаЭДО /DisableStartupDialogs
1cv8 DESIGNER /S<сервер>\<ИБ> /N<пользователь> /P<пароль> ^
      /UpdateDBCfg -Extension ПлатформаЭДО /DisableStartupDialogs
```

⚠️ **`/UpdateDBCfg` делать всегда.** Без него расширение числится загруженным, а его объектов
в базе нет: команды не появляются, HTTP-методы отдают 404.

⚠️🔴 **После установки снять «Безопасный режим».** И `/LoadCfg -Extension`, и программная запись
ставят расширение с `БезопасныйРежим = Истина`, а в нём **молча** не работают криптография и
исходящие HTTP-запросы — то есть ровно то, ради чего расширение и нужно. Снять флаг из кода
самого расширения нельзя («Изменение расширения конфигурации недоступно в безопасном режиме»),
нужен внешний канал: конфигуратор, COM-соединение или другое расширение.

Проверка после установки:

```bsl
Для Каждого Р Из РасширенияКонфигурации.Получить() Цикл
    Сообщить(Р.Имя + " " + Р.Версия + " активно=" + Р.Активно + " безопасныйРежим=" + Р.БезопасныйРежим);
КонецЦикла;
```

В норме `Активно = Истина`, `БезопасныйРежим = Ложь`.

## Настройка

### 1. Свойства объектов

Расширение хранит своё состояние в типовом механизме свойств
(ПВХ `СвойстваОбъектов` + регистр `ЗначенияСвойствОбъектов`) — своих регистров оно не заводит,
поэтому установка не требует реструктуризации базы и монопольного режима.

Завести до первой отправки:

| свойство | назначение | тип |
|---|---|---|
| `ОФД_ЭДО_СтатусДокумента` | статус отправки документа | Число (3,0) |
| `ОФД_ЭДО_ИдентификаторДокумента` | идентификатор документа у оператора | Строка (50) |
| `ОФД_ЭДО_ИдентификаторУчастникаЭДО` | идентификатор абонента у контрагента | Строка (50) |
| `ОФД_ЭДО_СтатусСвязи` | состояние приглашения/связи с контрагентом | Строка (50) |
| `ОФД_ЭДО_Фамилия`, `ОФД_ЭДО_Имя`, `ОФД_ЭДО_Отчество` | ФИО подписанта организации-продавца | Строка |
| `ОФД_КА_Фамилия`, `ОФД_КА_Имя`, `ОФД_КА_Отчество` | ФИО подписанта контрагента | Строка |

⚠️ Ресурс `Значение` регистра — **Строка(50)**. Списки и длинные значения туда не влезают,
поэтому кэши и настройки расширение держит в `ХранилищеОбщихНастроек` (см. ниже).

### 2. Параметры в `ХранилищеОбщихНастроек`

Объект `ОФД_ЭДО_НастройкиОбработки`:

| ключ | что хранит |
|---|---|
| `ОтпечатокПодписанта` | отпечаток сертификата КЭП (Base64) — **обязателен**, в коде его нет |
| `Хост` | адрес API оператора |
| `КлиентскиеНастройки` | XML-настройки движка вендора |
| `РеестрАдресов`, `ФактическиеМаршруты` | кэш адресов контрагентов и фактических маршрутов доставки |
| `ЗамокОтправки` | защита от одновременной отправки одного документа двумя сеансами |

Отпечаток задаётся так:

```bsl
ХранилищеОбщихНастроек.Сохранить("ОФД_ЭДО_НастройкиОбработки", "ОтпечатокПодписанта", "<base64>");
```

⚠️ **При перевыпуске КЭП прежний сертификат отзывается** — отпечаток нужно обновлять,
иначе подпись перестанет проходить.

## Ограничения и известные грабли

- маппинг в макете `НастройкаРеализация` **привязан к конкретной конфигурации базы**: он
  обращается к реквизитам документа реализации, именам видов контактной информации и составу
  перечисления статусов заказа. На другой базе эти места придётся сверить — они снабжены
  комментариями прямо в макете;
- маппинг лежит **в макете расширения**, а не в настройке базы ⟹ любая его правка требует
  пересборки `.cfe`;
- ⚠️ макет — это XML, а BSL лежит внутри его узлов. Сырые `<` и `>` в комментариях BSL ломают
  разбор макета, и сборка документов падает уже в бою. Экранировать (`&gt;`) или не писать;
- заливка `.cfe` с **тем же номером версии** возвращает успех, а работает прежний код ⟹
  поднимать `<Version>` при каждой сборке;
- после обновления первые запросы могут идти в переиспользуемый сеанс со **старой** сборкой —
  приёмку повторять, а не верить первому ответу.
